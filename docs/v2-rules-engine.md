# v2 clarification rules engine (`src/v2/rules/`)

Pure, deterministic TypeScript that decides what `/v2/search` asks after the models run. No model, no I/O, no state: the URL carries every answer, so the same input always gives the same output. Called by `GET /v2/search` (ISS-2499, see v2-search.md). Ticket: ISS-2697.

## Two calls around the search

- `decide(request, signals, tenant)` runs before Elasticsearch. It returns the internal emergency band (`emergency_band`, never in the response) and the cache rule (`cacheable`), the need states (`use` boosts, `ask` becomes an option, the rest is dropped), the urgency state, the candidate questions, and `count_codes`: the need codes the search must count.
- `finalize(decision, { counts, match, weak })` runs after the search (switch `V2_QUESTION_RULE_V1` on; off, development's engine in `legacy/` runs with `{ counts, strong_text_match: false }`). `match` (`concentrated`, `spread` or `none`, from `match.ts`) says what the returned hits say about the query words; `weak` is the weak-match flag. `finalize` picks the grid rule, keeps the questions of that rule, adds the counts to the options, ranks, and returns at most 3 questions. A 0-count option stays, shown with its 0 (switch off: it is dropped). `counts.by_code` is either an object (the codes were counted: a code missing from it has 0 results, since an Elasticsearch terms aggregation leaves out zero-count buckets) or `null` (not counted: not built yet, `clarify=never`, or the count failed; every option is kept, without a count). A needs question with fewer than 2 options is dropped. The emergency and time questions stay with every rule.

Rules (`gridRule`; switch on only). No results or a weak match comes first, then the match and the need level pick one:

- no results: the `no_match` question only, and the `phone_line` (`Call 211`, number 211).
- R1 (`match` concentrated, the keyword list names an org): no needs question.
- R2 (need level kind or likely): results, and a quiet `area:<T1>` question for a likely kind.
- R3 (need level area): one `area:<T1>` question per open area.
- R4 (no clear need, hits spread): the `spread` question, else the one in-play area question, else `start`.
- R5 (no clear need, `match` none): the `start` question only, with `notice` (`may_not_match`, R5 only) and the `phone_line`.

Needs never filter results; a used or confirmed need only boosts (`boost_needs`, never a Tier 1 together with its Tier 2).

## Inputs

- Request: `has_text`, `needs` (confirmed, URL order; Tier 1 or Tier 2 codes only, `N-X` is rejected with 400), `passed_needs` (same rule: an unknown code or `N-X` is a 400 that names it), `urgency` (`U-X` means "time not known" and counts as absent: the engine behaves as if none was sent), `has_content_word` (the text has a 2+ letter token that is not a function word; the soft card needs it), `clarify` (`never` keeps only the emergency question).
- Signals from ml-broker `search-classification`: 91 need scores (74 Tier 2, 16 Tier 1, `N-X`), top-level `urgency` `{level, score}` (beside `needs`, as ml-broker sends it; read only when the needs call succeeded), emergency `{status, score, floor_hit, calm_context, dv_shelter}`; `emergency: null` when there is no typed text.
- Tenant: `hotlines`, `ai_classification`. Start and no-match questions use the global default areas (Housing, Food, Money).
  - `hotlines` come from the Payload `search_config:<tenant>` Redis value, field `hotlines` (`tenantHotlines`: trimmed, at most 4). Empty or malformed: the engine's `DEFAULT_HOTLINES` (988, 911).
  - The start question's areas are the global defaults (`DEFAULT_TOP_AREAS`: Housing, Food, Money) for every tenant. There is no per-tenant count.

## Cutoffs (`config.ts`, `RULES_VERSION`)
- Emergency, in order: floor hit -> popup at score >= 0.65, else soft; calm context -> soft at >= 0.217, else none; DV shelter below 0.65 -> soft; >= 0.65 popup; >= 0.217 soft; else none. Error -> `unknown`, not cacheable.
- Cache rule (`cacheable`, ADR 0039 Decision 28): true only when the band is `none`, there is no emergency question (a caller `urgency=U-0` adds one with band `none`), and the needs call succeeded.
- Urgency: a caller level other than `U-X` is confirmed (`use`); `U-X` from the caller is ignored. From the model: < 0.8 drop (U-X); 0.8 to 0.93 ask; >= 0.93 use the model level.
- Needs: Tier 2 >= 0.97 use, 0.12 to 0.97 ask, below 0.12 drop. Tier 1 >= 0.8 (`tier1Use`) use, else drop; a Tier 1 code is never asked. The v1 hybrid need boost gate (`NEED_BOOST_GATE`) stays 0.97 for both tiers, so a Tier 1 need between 0.8 and 0.97 is `use` in the intent and the area question fires, but it adds no ranking boost.
- Area rule: each Tier 1 >= 0.8 whose own area has no Tier 2 >= 0.5 and none in use gets a which-kind question (per area, so a named need that already leans to a kind does not hide the others); every open area keeps its question, most uncertain first (`V2_QUESTION_RULE_V1`; off: `finalize` keeps the most uncertain one). When the keyword list names an org (`src/search/internal/name-match/name-match.ts`), no need question is asked.
- N-X means "need not yet known". It is internal: it is never an option and has no label. `nx` in the decision is true when no need is used and N-X scores >= 0.07, or the engine is given `N-X` as a confirmed need.
  A cutoff or rule change bumps `RULES_VERSION`.

Only the emergency "Yes" option offers `U-0` (Lucas 2026-11-13). A caller `U-1` to `U-4` removes the emergency question, also on a keyword floor hit; `U-X` counts as no answer (Decision 51 as written). ADR 0039 Decision 50 needs a follow-up line that lists the 3 emergency answers (`U-0`/`U-1`/`U-2`). `clarify=never` never removes it (Decision 26). The response has no top-level `emergency` block.

Each option is `{label, parameter, value, results_count}` (ADR 0039 Decision 55). `results_count` is the number of matching services, or `null` when the server did not count (all urgency options; need options when no count ran). Null means not counted; a counted code that is missing means 0, and a 0-count option stays in the question with its 0 (switch off: it is dropped). `parameter` is the URL parameter a pick adds: `needs` (start, spread, area and narrow options) or `urgency` (emergency and time options). The question has no `parameter`. `passed_needs` is in the enum, but no option emits it today: "None of these" stays the `none_of_these` flag, and the client sends the shown codes in `passed_needs`.

Needs questions allow several picks, an "Other" text box and "None of these". A confirmed Tier 2 need locks its area; a passed need is never offered again; an area with an area question gives no options to a narrow question in the same response. Importance tells the client how much a question matters; the engine still returns up to 3, ranked by `priority` (see Order), and never drops a question for low importance. The client (Norse) shows at most 3 questions before results.

## Order

Each question has a `priority`. The engine sorts high to low, then by id, and keeps the first 3.

- `priority = BAND_BASE[importance] + value`. Bases: critical 3, high 2, medium 1, low 0. `value` is in [0, 0.999], so a band never passes the band above it.
- `value = uncertainty x effort x split`, rounded to 3 places and capped at 0.999.
- Uncertainty, `emergency`: `4p(1-p)` of the emergency score (0.5 when it is missing).
- Uncertainty, `urgency_today` and `urgency_time`: `4p(1-p)` of the urgency score (0.5 when it is missing).
- Uncertainty, `start` and `area:*`: normalized entropy of the model scores of the need options, without N-X.
- Uncertainty, `narrow:*`: mean of `4p(1-p)` over the need options, without N-X; 0 when there is none.
- Effort: `1 - 0.05 x (options - 2)`, between 0.8 and 1. "None of these" does not count as an option.
- Split: with one counted option, `1 - 2 x |count / total - 0.5|`; with two or more, the normalized entropy of the option counts (even counts give 1, one dominant option gives near 0). Between 0 and 1. It is 1 when no option has a count (urgency questions, or `decide` before `finalize`).
- `decide` fills `uncertainty`, `value` and `priority` with split 1, and keeps each option's model score in `option_scores` (internal, not in the response). `finalize` recomputes `value` and `priority` after it drops options; when a question lost options, it first recomputes `uncertainty` over the options left, so a question cut to one option has uncertainty 0.
- The emergency question is always first, in both bands: `finalize` sorts it ahead of every other question before priority. Strong band: importance `critical` (the client shows a popup). Soft band: importance `high` (in-page card). A caller `urgency=U-0` hotline question stays `critical` (Lucas, 2026-11-13).
- `step` stays in the output for information only. It no longer sorts.

## Tests

`npx jest src/v2/rules`. `engine.spec.ts` runs the 40 real model outputs in `__fixtures__/golden-scores.json` (copied from ml-broker's golden file) 1,000 times each and checks the output never changes.

The question has no `level` field (Lucas, 2026-11-13). A client reads `importance` and `type` to choose the display. The popup and soft bands of the emergency question give the same `type`, `reason`, stem, options and hotlines; `importance` tells them apart (`critical` = strong band, `high` = soft band).
